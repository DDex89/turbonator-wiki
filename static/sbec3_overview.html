SBEC3 (1996+ Neon / 2G Eclipse-Talon): hardware and firmware overview

Since 1996 the Neon (and the second-generation Eagle Talon / Mitsubishi Eclipse 420A engine) use a different controller, the SBEC III, with a Motorola 68HC16 CPU in place of the FCC's 68HC11. It is a separate reverse-engineering project, a companion to neon-fcc-firmware: github.com/DDex89/neon-sbec3-firmware. The annotations are made on one reference image and carried over to the other ten by matching routines between programs (see porting); where a routine or table has not been matched yet it keeps a numeric placeholder name. This page, calibration, tuning notes and reflashing cover it the same way the FCC pages cover the 1995 controller.

Stock 128 KB engineering update (2026-11-27)

The architecture below primarily describes the SBEC3 256 KB reference 05293190AC. The addresses in this update apply to the two listed stock 128 KB SBEC3 images. FCC has its own 68HC11 address map.

The historical names EepromWrite947, EepromWrite949 and EepromWrite94B correspond to the first three symbols above, in that order. The VSS event counter, CCD distance delta and SRI mileage request are separate values. SRI changes at request time. Physical distance scaling and interrupted writes remain open.

The 1997 image retains six additional history bytes at $F8092–$F8097 on warm reset and includes them in the retained-RAM checksum. Cold reset and ClearFaultHistoryAndCurrentState clear them. The isolated readiness and pass-side OBD checks preserved them in the tested cases. Other computed writers, normal nonzero use and hardware timing remain open. In the isolated misfire-aging checks, the threshold path also cleared the six bytes by calling ClearFaultHistoryAndCurrentState.

In isolated failure-side ObdFaultProcess tests with aligned stock descriptors, the 1997 image preserved $F8092–$F8097. For the 1997 Bank 1 descriptor at ROM $1F056, ObdFaultCondition set bit 7 of RAM $F870E in the tested states. The code also accesses other bits of this byte. Its overall role and normal caller reachability remain open. See the failure-side audit.

The flash checksum check is ChecksumCheck at $1A500 on 04887050 and $1CDB8 on 05293013AC. It compares the 8-bit sum to the part-number byte at ROM $03DE0 ($50) and $03E0B ($13), respectively. NvChecksum covers retained RAM.

An isolated full freeze-frame capture writes 14 bytes at $F80CF–$F80DC on 04887050 and $F80D7–$F80E4 on 05293013AC. The full capture also writes a LookupResult byte at $F83B0 and $F82FE respectively. A higher-priority capture of the same ID updates only the priority byte.

See per-ROM symbols and dependencies, EEPROM audit, architecture, SCI/PIT/OBD, fuel and CCD, DTC symbols.

Checksum

The 8-bit sum of every byte of the image equals the last byte of the part number (header + 3); header + 13 is the correction byte that is adjusted to make it so. This is the scheme of checksum.py in SBECBootLoader, and it holds for all eleven images. It is the same idea as in the 1995 FCC firmware, where the sum must equal the last byte of the part number at $B805. [code]

In the code the check is ChecksumCheck ($2191E), called from CheckPowerDown (the power-down path) once input bit $1000.3 has read set 32 times in a row, not at start-up. SumBanks ($2195E) adds the bytes of two banks at a time (0 and 1, then 2 and 3) in 16 KB steps; the result is compared with ChecksumTarget ($0305 in 05293190AC) and a mismatch reports P0601. It is a plain 8-bit sum, not a CRC. TunerPro does not correct it; run tools/fixsum.py –fix on an edited image. [code]

In family A, header + 13 is $FF; the byte after the repeated part number ($D3 / $06) is probably the correction byte there. [inferred]

Next steps

Stage 2 is done, see tools.md: disassembler, assembler and source generator, with all eleven images rebuilt byte for byte. It also confirmed that Z points at RAM ($F8000) and that extended addresses read the calibration in bank 0. The reference image is 05293190AC, because outside reference addresses exist for it. The project owner's 1996 Neon controller is expected to be a 128 KB, 2 KB RAM unit; its family will be reached by porting the annotations.

Hardware set-up (reset code)

Reset ($0D08C) configures the controller before anything else runs:

Item Setting Result
Stack, Z, extension registers SK = ZK = $F, SP = $8FFE, IZ = $8000, EK = 0 Z = $F8000 (RAM start); extended addresses read bank 0 (calibration)
Clock SYNCR = $7F80 16.78 MHz from the 32.768 kHz reference
Internal SRAM RAMBAH/RAMBAL = $FF8000 4 KB at $F8000-$F8FFF
Periodic interrupt PITR = 7, PICR = $0338 every 7 x 4 / 32768 s = 0.854 ms, level 3, vector $38
Software watchdog SYPCR = $94 serviced by KickWatchdogs
Chip selects CSBOOT, CS0: base 0, 256 KB; CS2: base $F9000, 2 KB flash; one external device at $F9000-$F97FF
GPT ICR = $B340 level 3, vectors $40-$4B; the pulse accumulator input is the adjusted channel
SCI / QSPI QILR = $1B, QIVR = $FE SCI vector $FE, QSPI vector $FF

The external device on CS2 is reached as $1000,Z-$17FF,Z; the code uses 61 different addresses there. It is a timer, output driver and bus interface chip, described below.

Reset also counts the reset causes: the bits of the SIM reset status register RSR are added as 4-bit counters into ResetCountsExtSw ($08,Z: external reset, software watchdog) and ResetCountsHltPow ($09,Z: halt monitor, power-on). ResetCheckWord ($06,Z) is rewritten by every main-loop pass and checked at reset to tell a warm restart from a cold start.

Single bits of RAM flag bytes are described in annotations/bits.json. The generator writes the meaning after every BSET/BCLR/BRSET/BRCLR on such a bit and under the byte in 00_equates.asm. The bits of FaultSet00-1B and FaultMem00-1B come from the fault table itself: each row gives its byte, its bit and its P-code.

The CS2 device ($F9000)

The SIM chip selects are set in the reset code: CSBOOT and CS0 cover the 256 KB program flash (CSBOOT reads, CS0 only writes, for programming), CS1 and CS3-CS10 are off, and CS2 opens a 2 KB window at $F9000 with 16-bit data, read and write, one wait state. The program reaches it as $1xxx,Z. It is a peripheral chip, not memory: only offsets $000-$084 are used, and what the code does with them makes it a combined timer, output driver and bus interface. The register names in ram.json start with Io; their bits are in bits.json.

Offset Name Use
$000-$001 IoInputs0, IoInputs1 discrete inputs: key off (bit 3, probably), ASD output present (bit 2, probably), leak detection pump switch, speed control switch; the switch map is collected from this word; feedback bits of some drivers
$002-$003 IoStatus2, IoStatus3 driver and knock status bits
$006-$010 IoTimer06 … IoIrqStatus timers and the interrupt registers: IoIrqEnable ($00C) and IoIrqStatus ($00E, cleared by writing ones)
$016, $01A IoBusData, IoBusStatus received bus byte and its error bits ($000E), read by the IRQ4 and IRQ2 bus handlers
$012-$020 IoCtl12, IoCfg14 … IoCfg20 control and set-up words written at reset and checked by HardwareCheck
$024-$038 IoOcChan0-5 six output channels, set by OcOutputsReset and fired by the output test
$03E-$050 IoPwmC18A/B, IoFanPwmA/B, IoPurgePwmA/B PWM period and duty pairs (output C18, radiator fan, purge)
$056-$060 IoInjector0-5 six injector timers written by FuelEventCalc and InjectorSequence
$062-$06E IoDriver62 … IoDriver6E one word per low-side output: bit 13 output on, bits 15-14 driver status (LDP solenoid, lamp/C18, tuning valve, fan, purge, generator field)
$070-$07A IoEvent70 … IoEvent7A six words cleared by EventCorrections
$07E-$084 IoPwmC18Read, IoFanPwmRead, IoKnockRead read-back of the PWM outputs and of the knock set-up

IRQ2 comes from this chip. Isr_IRQ2 reads IoIrqStatus: a bus event (bit 3 of the low byte) goes to Irq2Dispatch and the CCD/PCI handler, a timer event (bit 1 of the high byte) is counted in Irq2Counter for the misfire segment times, anything else clears all flags. IRQ4 runs Irq4BusHandler, which reads the received byte and its status from IoBusData/IoBusStatus and compares it with the byte just sent (bus arbitration). So the CCD (or PCI) interface is part of this chip too.

The handlers of the interrupts that should not occur (IRQ1, IRQ3, IRQ5-IRQ7, OC1, pulse accumulator overflow) disable their own source and jump to UnexpectedInterrupt, which sets a bit per source in UnexpectedIrqFlags ($00,Z) and saves two words of the interrupted stack frame at UnexpectedIrqStack4 ($02,Z) and UnexpectedIrqStack6 ($04,Z). That is a record for diagnosis, not a recovery.

Fast scheduler: the PIT interrupt

Isr_PIT runs every 0.854 ms. Unless O2HeaterSample ($0550,Z) is set it increments PitTickCounter and LoopTickCounter and then picks work by the low bits of PitTickCounter:

Ticks Period Work
odd 1.71 ms HighRpmTimerPit, SciPitService; MtvTiming and TuneValve2Control if calibration bits $0335.5 / $0335.7 are set
2 mod 4 3.42 ms starts an ADC conversion sequence (ADCTL1 = $24), then ChargeControl2 or ChargeControl (calibration bit $0338.1)
4 mod 8 6.84 ms IacStepperDrive
0 mod 8 6.84 ms nothing

After that, on every tick: FanPwmOutputCheck if calibration bit $0334.4 is set, a counter for FieldPwmCounter ($0DC0,Z), and every 24 ticks (20.5 ms) CcdTransmit or PciPitTick, chosen by calibration bit $032E.2.

Background scheduler: the main loop

MainLoop ($0DC36) makes one pass every 14 PIT ticks, about 12.0 ms:

  1. 33 routines on every pass, starting with KickWatchdogs and MainLoopCounters.
  2. One group of routines chosen by the lowest set bit of MainLoopCounter, the same scheme as in

the FCC:

Lowest set bit Period Routines
0 2 passes, 24 ms 9 (SkimEepromSave … PwmC18CircuitCheck)
1 4 passes, 48 ms 3 (ChargeDeficitCalc, BatteryVoltsUpdate, AsdRelayCheck)
2 8 passes, 96 ms 13 (SecurityState … LimitReasonCode)
3 16 passes, 191 ms 5 (PciLinkCheck … WotLeanMonitor)
4 32 passes, 383 ms 5 (KnockLearnDecayStep … BusTempFlag)
5 64 passes, 766 ms 2 (FlexFaultReport, FuelSenderMonitor)
6 128 passes, 1.5 s none
7 256 passes, 3.1 s 6 (SriMileageStore … BusStatusByte)
  1. About 60 more routines on every pass; one of them is chosen by calibration bit $032E.2

(CcdReceive, or PciReceive and QspiCheck).

  1. CheckPowerDown, then wait until LoopTickCounter reaches 14, calling MeasureLoopTime

meanwhile; clear the counter and start again.

MainLoopCounters also keeps slower time bases: Count3s (every 256 passes) and Count191ms (every 16 passes), both saturating at $FF, and MainLoopPhaseMask ($0C3B,Z). Bit n of MainLoopPhaseMask is set once every 2^(n+1) passes; 127 instructions test it with BRCLR MainLoopPhaseMask,Z,#mask,… to run part of a routine at a lower rate.

Two communication variants (CCD or PCI bus)

Calibration bit $032E.2 is tested in 30 places. In several of them it selects between two sets of routines: in the main loop (see above), in the PIT interrupt (CcdTransmit / PciPitTick), in Isr_IRQ2 (Irq2BusHandler / PciIrq2Start) and in the reset code. Reading the receive side confirms two vehicle-bus interfaces:

  • CcdReceive takes one-byte message IDs with up to two data bytes from two receive buffers

($89A2, $89A8). CcdTransmit sends a fixed rotation of messages built by small routines; each message is an ID, two data bytes and a checksum byte (the sum of the other three). The message set includes MAP, throttle with the speed control set or resume speed, coolant and battery temperature, battery and target voltage, engine rpm with the idle target, baro and air temperature, fuel used and distance pulses, and the VIN one character at a time (Vin01-Vin17).

  • PciReceive takes frames of up to 11 bytes; the low bits of the first byte are tested as a

header and the second byte selects the handler from a jump table at $3105A. Its handlers store the same values as the CCD ones. Together with the header byte this points to J1850 PCI, but the bus type is still an inference.

The two variants also use different hardware. The CCD bytes go through the CS2 chip (IoBusData, IoBusStatus, IRQ2 and IRQ4, see above). The PCI frames go over the QSPI: QspiSendFrame copies a frame into the QSPI transmit RAM, PciRxFrame reads the received frame from the receive RAM and checks a one-byte sum, and PciTimeoutRestart arms the frame timer. So in the PCI variant a separate bus controller sits on the QSPI and does the bus framing itself; a J1850 controller with an SPI port fits that, but the part cannot be told from the code.

Both receive routines handle the SKIM (immobiliser) exchange: messages $0B and $C2 carry the status and the key data (SkimStatus, SkimData0-SkimData4). SkimKeyCheck ($320D6) works out the expected key from the VIN bytes, and a wrong key reports P1685.

Diagnostics over the SCI line

Isr_SCI calls SciInterrupt ($3343C). The diagnostic commands are dispatched through the jump tables at $35000, $3509C, $350CC, $350DC and $35BB0. Among them is a service that writes a received routine byte by byte into RAM at $F8700-$F87FF (DiagWriteRamByte) and, after checking its length, its checksum and the final RTS, runs it (DiagRunRamCode, JMP $F8700). A tester can therefore run its own code in the controller without reflashing. This is separate from the bootstrap mode that third_party/SBECBootLoader uses.

The same line also carries a high-speed logging mode (SciLogReceive): command bytes $F2 and $F3-$F6 set the mode bits in SciLogFlags and $FE leaves the mode; after that, each received byte selects a value that is sent back (from a RAM index list, or a word from a bank-3 page chosen by $F3-$F5). SciRequestReceive takes the ordinary requests (DiagCommand, DiagParam1-DiagParam3); a fixed byte sequence ($F8, $F7, $F5, $F3, $14), tracked in SciUnlockState, switches to command $52.

See reflashing for the separate bootstrap mode used to erase and rewrite the flash.

Unreached code

Thirteen routines (about 2.2 KB) are never called, jumped to or pointed at: an older copy of the flex fuel learning with its helpers ($17512-$17F2x and $18264), a rpm-window flag and fuel hold table ($12BFA), a crank period delta, a period tracker and five small arithmetic helpers in bank 0 (two of them, $0C9F8 and $0CA5C, use the bit-mask words at $0C9D8), and UnusedCylSparkOverride ($1E65C). A fourteenth piece, UnusedCylSparkSet ($1E418), sits inside SparkEventCalc (in its spark start ramp part) behind a BRA that always skips it. Together they are the remains of a per-cylinder spark override: the skipped block fills CylSparkOverride (RAM $0D7A, one byte per cylinder) from CylSparkOverrideBase ($04A2) plus CylSparkOverrideValues ($04A3, 6 bytes), and the uncalled routine would return that value instead of the spark advance for cylinders selected by a byte from the bus. It replaces the angle rather than adding to the spark map, so it looks like a test function. The live GetSparkAdvance has the same interface (cylinder in A, angle back in A): its three callers still load CylinderIndex into A, which it ignores, so it is the stand-in for that routine. The same code, equally skipped, is in families D and E; families A, B, C and G do not have it. The calibration bytes are 0 and appear in the XDF under “Not used”. They decode cleanly and end in RTS (the skipped block falls through to the code after it), so they are listed in annotations/analysis.json (unreached_code) and disassembled; their names start with Unused. The string COPYRIGHT 1996 CHRYSLER CORPORATION sits at $07000.
