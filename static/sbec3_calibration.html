SBEC3: calibration

See also SBEC3 overview and tuning notes (TunerPro, porting, open questions). The full per-image table catalogue is generated into docs/catalogue/ in the repository.

Scope of addresses and option masks

The detailed tables below use the 256 KB reference 05293190AC unless stated otherwise. For stock A/B 128 KB images 04887050/51 and 05293013AC/14AC, the reviewed FlexFuel option is $0324 mask $01, and manual transmission is $0325 mask $20. For family C (05007038/05293148AA), manual transmission is $0324 mask $08. These are family-specific metadata corrections, not instructions to change the stock settings. Use the matching XDF; runtime RAM/MMIO symbols are not editable ROM calibration addresses. See stock XDF metadata review and symbol and dependency review.

Where the calibration lies

The calibration is in bank 0, between the header at $00202 and the start of the code at $08000. The reset code sets EK = 0, so the code reads it with plain extended addresses (CMPA $19DC). Nothing in the code writes there: the area is read-only.

The code refers to it in two ways:

  • Tables, passed in X to one of four lookup routines (LDX #table, JSR Lookup2D). The lookup

routines force XK = 0, so every table is in bank 0. 410 tables are found this way, between $0398 and $ABD7 (two small ones lie among the bank 0 code).

  • Constants, read directly: 1,449 different addresses, mostly with CMPA/CMPB (thresholds),

LDAA/LDAB and LDD/CPD (16-bit values). Configuration bits at $0328-$0340 are tested with BRSET/BRCLR. See constants and option bits.

Table formats

All values are bytes. The formats follow from the lookup routines:

Format Routine Layout 2GNT type
2D Lookup2D ($0C08E) n, flags, then n pairs (x, y), x ascending C
2D (y, x) Lookup2DRev ($0C36A) n, unused, then n pairs (y, x)
3D Lookup3D ($0C214) rows, columns, signed flag, column axis (one byte per column), values row by row A
3D, no axis Lookup3DNorm ($0C28C) rows, columns, signed flag, values row by row B

Fault table: see below (2GNT type D).

2D. The input is compared with the x values; between two points the result is interpolated linearly, outside the range it is the first or last y. The flags byte selects the arithmetic: $80 unsigned (320 of the 353 tables), $20 signed y, $10 steps without interpolation, $40 a zero y counts as 256. Many 2D tables are followed by unused bytes up to a 12-byte slot (five points); whether a table may be lengthened into that space has to be checked per table.

3D. The row input is a position 0-255 spread evenly over the rows (row = position x (rows-1) / 256). It usually comes from a 2D scale table that converts MAP into that position: the part-throttle tables use PartThrottleMapScale, the WOT tables WotMapScale. The column input is searched on the stored column axis (Lookup3D) or is also a position 0-255 (Lookup3DNorm). The result is interpolated in both directions. Sizes in this image: 17 x 17, 9 x 17, 9 x 9, 5 x 9 and 5 x 5.

The signed flag ($FF) makes the values two's complement; the source shows them as negative decimals.

All of these were checked against the code: each is read where 2GNT says, with the format above. One correction: 2GNT shows the rev limit as two cells starting at $19DB (resume and limit), but $19DB holds $FF and is never read; the code compares rpm with $19DC or with $19DE. The 2GNT page calls the fuel tables “msec”; the code shows that they are corrections applied to a pulse width computed from MAP (next section).

tools/autoname.py merges the hand names (python3 tools/autoname.py hand.json) and still gives a structural name to any table found later without a hand name: the subsystem prefix (taken from the routine that reads the table and the scheduled routine above it), then the inputs (Coolant, Rpm, Map, V0A91 for an unnamed RAM variable, …) and a number when the name repeats. Such entries are marked “auto”: true and get a * in the catalogue.

Constants and option bits

tools/constants.py finds every byte or word the code reads directly with extended addressing and that is not part of a table: 1,449 of them in 05293190AC (1,264 bytes, 181 words, 4 longs; two more, the row counts after FaultStatusMap, are named by hand because the code reaches them through X), among them 21 option bytes tested with BRSET/BRCLR (120 bits used). They are kept with the tables in the scalars of annotations/tables.json, so the sources show CMPA >IdleCoolantMin instead of CMPA $2853, the catalogue lists them with value and physical value, the XDF has them as constants (and every option bit as a flag), and the port carries them to the other images (from 239 in family A to 1,404 in family E).

All 120 used option bits are described in annotations/bits.json. The polarity was read from the code: most bits switch a function on (BRCLR skips it when the bit is clear), a few switch it off (for example $033A.7 skips the idle flare check, $0328.0 the SKIM handling). Bits that only pick one of two code paths without a clear purpose are described as “selects a branch in …”. Settled ones include $032C.7 closed loop off, $032C.6 flex fuel, $032E.6 manual transmission, $032E.2 PCI bus instead of CCD, $032F.7-4 the O2 sensors fitted (upstream 1 and 2, downstream 1 and 2) and $033F.7-4 the matching heater monitors. The XDF puts the text in the description of each flag.

For each constant the script looks at how it is used: what the register held before the compare, add or subtract (LDAA >CoolantTemp,Z then CMPA $2853), or what a loaded value is compared with or stored into. That gives the unit (temperature, rpm, kPa, volts) and a structural name: the prefix of the tables of the same routine or the subsystem, the variable, and the role (Thresh for a compare, Adder, Offset, Factor, Init for a value stored into RAM, Value otherwise), numbered when repeated. All 1,451 constants now have hand names from the code that reads them; where the purpose is not certain the description says “probably”. The structural name and the * in the catalogue remain only for constants found in a new image and not yet named. Word rpm values use the unit rpmw (rpm = x / 8).

Fuel pulse width

CalcFuelPulse ($11F40) runs from the input-capture 1 interrupt, that is on every reference event:

  1. Part throttle or WOT is chosen by FuelModeFlags ($0771,Z) bit 5; this selects the constants, the scale table

and the fuel table.

  1. Base pulse width = (Map - MapOffset) x (256 + K) / 16, or zero if MAP is below the offset. With

calibration bit $0337.2 set, MAP is first raised to the lowest point of the part-throttle scale.

  1. The fuel table gives a signed value v (rows by MAP through the scale table, columns by

EngineRpm, whose high byte is rpm / 32); the base is multiplied by 1 + v / 256.

  1. BaroFuelAdder ($080E,Z) is added and the result is stored in FuelPulse ($07E2,Z) and Temp4F6 ($04F6,Z).

So the fuel tables work like a volumetric-efficiency correction on a linear MAP model, with the two constants setting the slope and the zero point. Dead time, temperature and other corrections are applied elsewhere (stage 5).

InjectorDeadTime is looked up with BatteryVolts2 ($0A51,Z) as input. 2GNT lists a fix that changes this to BatteryVolts ($0A50,Z) (BatteryVolts); who writes $0A51 has not been checked yet.

Flex fuel. The program supports flexible-fuel vehicles: FlexSensorCheck checks the fuel composition sensor (FlexSensorRaw, $0A8E,Z) and the flex-fuel learning code (FlexLearn…, around FlexLearnMain) learns the ethanol content from the oxygen-sensor trims (FlexEthanolLearned $0197,Z, 0-170, and FlexEthanol $0198,Z). The ethanol content then selects rows in the Flex… fuel and spark tables and in the cranking table. Calibration bit $032C.6 enables it; in 05293190AC (a gasoline car) the flex tables are neutral.

Fault table

FaultTable ($4052) has 256 rows of 10 bytes:

Byte Content
0 row number
1 trigger count
2 blink code (BCD, as flashed by the check-engine lamp)
3 attribute bits
4, 5 mask and byte offset of the fault bit in the fault bit array
6, 7 P-code (BCD): $03 $40 = P0340
8, 9 unused (zero)

83 rows carry a P-code; the list is in the catalogue. Codes for cylinders 5 and 6 (P0205, P0206, P0355) are present, so the program also covers six-cylinder engines.

OBD monitor table and condition lists

ObdMonitorTable ($20000, in the code area) has 16 rows of 20 bytes, one per OBD monitor, read by ObdMonitorMain: the record offset, the monitor status byte (MonStatus*), the run period (low six bits of byte 5, tested against MainLoopCounter), the fault table row of the monitor's P-code, the addresses of three condition lists, and the result byte and bit. The rows show which status byte belongs to which code: MonStatusCatBank1/2 are the catalyst monitors (P0420, P0432), MonStatusO2Resp1/2 the O2 response monitors (P0133, P0153), MonStatusO2Sensor1-4 the heater monitors (P0135, P0155, P0141, P0161), and the fuel system monitors give P0171/P0174 for “too lean” (adaptive at its upper limit) and P0172/P0175 for “too rich”. The fuel system routines and constants were renamed after this (FuelSysTooLean//, FuelSysTooRich//).

ConditionTable ($20B1C) checks such a list: a count, then 4-byte entries of RAM offset, test and mask or threshold. Test 0 requires all masked bits clear and test 2 requires them all set. Test 4 requires an unsigned value strictly above the threshold and test 6 requires it strictly below. The check fails at the first unsatisfied entry. The 48 lists lie in bank 0 between $33CA and $4015 and are laid out in the source with each entry decoded, for example CatBank1Conds1: the catalyst monitor runs only while none of 19 bytes of stored faults (FaultMem*, about 70 P-codes) are set. These lists are calibration: changing them changes which faults suspend which monitor.

On the 256 KB reference 05293190AC, FaultStatusMap starts at $758C. ObdFaultReport searches 22 ten-byte rows within that table, starting at $75FA. FaultTwoTripRows is the count byte ($16) at $7746. The prior-failure bytes are ObdPriorFailSwitch, ObdPriorFailO2 and ObdPriorFailMisc (Z+$009D–$009F, historically MonFlags09D–MonFlags09F). The matching result bytes are SwitchMonFlags, O2MonFlags and ObdResultMisc (Z+$0658–$065A, with MonFlags65A the old name for the last byte). A first failure sets the prior flag. A repeat with the result bit set can report the fault, and a pass clears both bits. In modeled warm resets of the audited 256 KB images, prior-failure bytes survived and current-result bytes cleared. Modeled cold resets cleared both groups. Physical standby retention, key timing and the remaining caller conditions are open.

On stock 04887050 and 05293013AC, the main loop selects FaultPendingAge at MainLoopCounter = $80, once per regular 256-pass rollover. The routine ages the two pending faults and the separate pass-recovery state. The time in seconds depends on ECU main-loop execution. The $75FA qualification table and its symbols above apply to 05293190AC. See Fault qualification and periodic pending-counter service.

BitCollectMaps ($713B, 29 maps of 32 bytes) supplies CollectBits with eight RAM offset, mask and output-bit entries per map. It builds bytes for switch inputs and for status sent by SCI and bus messages.

Lists of RAM addresses in the code banks are laid out with each word named: the EEPROM map (EepromShadowMap, $38448: EEPROM word and the RAM copy), the descriptors of the O2, O2 heater, downstream O2 and catalyst monitors, the OBD record pointers, the CCD transmit rotation and eight lists the SCI diagnostic service probably sends from (DiagDataList1-8).
