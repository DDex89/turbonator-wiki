See also FCC overview, fault codes and tuning notes. Background and the full generated reference: neon-fcc-firmware.

Findings

  • B4C2 is a code base that the spreadsheet does not list (5269646, rev C of 4874154).
  • The revision letters are not in code-base order: for 4874154 rev C is on B4C2 and rev D on B4F3,

so the letter does not tell which program version is newer.

  • Checksum: five images fail the $B805 checksum. In each of them $FF50 was changed and the

8-bit sum is $9C, so they were saved by an editor that forces the sum to a constant instead of the $B805 byte. On a B559 calibration this sets code 53. The unedited images all pass with $FF50 = $FF.

  • EEPROM window: several images carry data in $B600-$B7FF. That range is the HC11's internal

EEPROM, which the CPU sees instead of the chip, so these bytes have no effect; they show that the file was read from a programmed ECU or saved by a tool.

  • 4874157 (SOHC racing) and 4874164 (DOHC racing) have EGR enabled; their rev B, 5269718, has it off.
  • The Mopar 5007033 keeps the EGR bit in CONFIG set, but its EGR windows (EGR21, EGR23, EGR27

and the byte after it) are set to $FD/$FE, which the engine never reaches, so EGR is never enabled.

The calibration layout differs between code bases (for example the fault descriptor table is at $D4E9 in B559 and at $D4E3 in B4CC), so tables must not be copied byte for byte between them.

B559 compared with B4CC

The annotations of this repository were made on B4CC and ported to B559 with tools/port_base.py (see building.md). The comparison below comes from that alignment: code part 2 ($E229-$FFD5) is identical, and in code part 1 41,653 of 41,677 B4CC bytes have an exact counterpart in B559. [code]

B4CC is B559 with calls removed. The B4CC program is 141 bytes shorter. About 100 of them are the three temperature features listed below; the rest are jsr instructions that B4CC no longer has. The called routines are still in the B4CC ROM, byte for byte, but nothing reaches them there. [code]

Routine Called from (B559) What B4CC loses
ObdMonitorScheduler MainSubLoop All ten OBD-II monitors (see diagnostics.md)
ControlPurgeSolenoid_MM MainSubLoop Purge duty calculation: the on/off times sent to the companion chip in register frame $58 stay at their reset value. The separate on/off logic at $B290 (OutputDriverBits bit 5) still runs in B4CC; which of the two switches the solenoid at pin 16 is not confirmed yet
DetermineIndividualInjectorTrims_MM MainSubLoop Individual cylinder fuel trims
CalculateVariableRevLimit_MM MainSubLoop Variable rev limit; VariableRevLimit stays at $FF from reset, only the fixed limits act
CheckIfCheckEngineLightShouldBeOn_A_MM, _B_MM MainSubLoop Charge-warning lamp logic (OutputBits2 bit 4); despite the name not the MIL. Only the fan code (with CONFIG2 bit 6 set) and the DRB tests still touch the bit
EmmissionMaintenanceRemider1_MM MainSubLoop Emission maintenance reminder record in EEPROM, code 62
VerifyOperationOfDownstreamO2Sensor_MM MainSubLoop Downstream O2 sensor check (code 21)
DecrementDSO2SensorDiagnosticCounter_MM MainSubLoop Downstream O2 diagnostic counter
VerifyOperationOfAmbientTempSensor_MM MainSubLoop Key-on plausibility check of the air temperature sensors (code 23)
CheckErrorMaskingAndSetCodes_MM SubLoopA A speed / TPS related check (not decoded yet)
FurtherMAPAndBaroDiagnostics2_SM SubLoopC MAP versus TPS rationality check (code 24)
IncrementOrClearKnockDiagCounter_SM SubLoopC Knock sensor signal check (code 16)

So the racing / Mopar code base runs without OBD-II monitors, the purge duty calculation, cylinder trims, the variable rev limit and several sensor checks, which fits its use. The fault descriptors of these checks are still in the calibration and may be enabled, but nothing reports them. [code]

Code only in B559. Three short additions, all using the same start temperature: BatteryTemp, or AmbientAirTemp when CONFIG2 bit 5 is set. [code]

Where (B559) What it does Calibration (B559)
Reset init, $9202-$9224 Sets the purge delay PurgeDelayTimer ($021C): colder than PurgeDelayTempCold gives $FFFF, colder than PurgeDelayTempWarm gives PurgeDelayTime, warmer gives no delay $C983, $C984, $C985-$C986
ControlPurgeSolenoid_MM, $9CF9-$9D1D While the delay runs, the throttle is closed and the car is below MPHREF, counts the delay down (once per Counter_MainLoop wrap) and keeps purge from running -
ExhGasRecirc_MM, $B257-$B272 EGR only above EgrTempOn; once on, it stays on down to EgrTempOff $CB3C, $CB3B

Values in the factory images (temperatures in °C = count − 128, see engine_control.md; one Counter_MainLoop wrap is 256 × 10.75 ms = 2.75 s): [code]

4874154-4874165 5013113
PurgeDelayTempCold $6E = −18 °C $6E = −18 °C
PurgeDelayTempWarm $8A = 10 °C $84 = 4 °C
PurgeDelayTime $0221 = 545 wraps ≈ 25 min $028E = 654 wraps ≈ 30 min
EgrTempOff / EgrTempOn $73 / $74 = −13 / −12 °C $7B / $7C = −5 / −4 °C
MPHREF 7 = 3.5 mph 5 = 2.5 mph

So after a start below 10 °C the factory calibration keeps the purge off while the car stands or creeps until about 25 minutes of such time have passed (practically for the whole trip below −18 °C), and EGR is not used below about −12 °C. [code]

Layout consequences. Because of these additions the B559 calibration has 4 extra bytes after the idle purge table and 2 after the EGR constants: B4CC addresses $C983-$CB36 are 4 higher in B559 and $CB37-$DFF7 are 6 higher. RAM is the same except the DRB RAM-program buffer, which moved from $021C to $021E to make room for PurgeDelayTimer. [code]

B4F3 and B4C2 compared with B4CC

Both were ported the same way (annotations/bases/B4F3/, annotations/bases/B4C2/) and all their images rebuild byte-identically from src_b4f3/ and src_b4c2/. Their RAM and calibration layouts are the same as B4CC's: every one of about 1,020 calibration references in the code points to the same address. [code]

B4F3 is B4CC plus the thirteen calls. The only difference is in MainSubLoop, SubLoopA and SubLoopC: B4F3 has the same thirteen jsr instructions as B559 (39 bytes), so its OBD-II monitors, purge duty, cylinder trims, variable rev limit and sensor checks run. It does not have B559's three temperature features (purge delay, EGR temperature gate). [code]

B4C2 is B4F3 with two more differences: [code]

Where B4C2 B559, B4F3, B4CC
J1979 PIDs $14 / $15 (O2 voltages) Sends the raw A/D byte Scales by $03ED/256 to 5 mV per bit, $FF from $41 up; B4C2 therefore shows about a quarter of the real voltage on a scan tool
Companion chip status 6 (AisDriveRoutine) Sets BitFlags69 bit 1 unconditionally Only when BatteryVolts is at least BTVAIS

B588 (1993)

5293121 is a different generation. Its calibration is larger (code part 2 starts about $EB5E instead of $E229) and its header and vectors differ. A first alignment finds a counterpart for about 83 % of the B4CC code part 1 and 60 % of part 2, spread over some 2,000 pieces, so it is not ported yet. [code]

Type codes: 0 = 2D point-slope curve, 2 = 2D curve (other format), 3 = byte constant, 4 = word constant, 5 = bit flags, 7 = 3D map (rows x cols), 9 = address list, 11 = O2 ramp kick table, 17 = 3D map with its own axis.
