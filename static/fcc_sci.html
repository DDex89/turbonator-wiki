'95 Neon FCC: diagnostics and communication

This complements SCI bus technical info with the FCC side of the protocol: the DRB commands, the actuator tests, the OBD-II monitors, ISO 9141 / J1979, and the separate link to the I/O companion chip and the CCD bus. Source: neon-fcc-firmware.

The controller has two diagnostic links on the same SCI port (connector pins 9 receive and 30 transmit). One is the Chrysler DRB protocol, used by the DRB II/III scan tool, MP Scan-type loggers and code download. The other is ISO 9141 for generic OBD-II scan tools. The fault codes themselves are listed in fault_codes.md.

Confidence: [code] = follows directly from the code, [inferred] = likely, not yet confirmed.

Serial settings

Mode BAUD Rate (8 MHz crystal, E = 2 MHz)
DRB normal $22 7812.5 baud [code]
DRB high speed (command $12) $01 62500 baud [code]
ISO 9141 $12 10417 baud (10.4 kbaud) [code]

The rates match the known Chrysler SCI and ISO 9141-2 rates, which also confirms the 8 MHz crystal.

DRB protocol

DRBIISerialCommunications_MM ($4FDB) runs from the main loop. It echoes every received byte. A command byte from $10 to $25 is kept in DRBPointer1. DRBSerialToggles says how many parameter bytes follow (one or two), and these go to DRBPointer2 and DRBPointer3. DRBIIOuput_MM ($5061) then calls DRBFunctionTable[command - $10].

$13 SetupATM Starts actuator test n (parameter, up to $40); refused while the engine runs [code]

OBD-II monitors (dormant in the two calibrations in this repository)

The code contains a complete set of OBD-II monitors driven from a table, ObdMonitorTable at $E939: ten records of 14 bytes. Each record holds the monitor routine, its status byte in RAM, a scheduling mask, the fault descriptor it reports and three calibration pointers for its enable conditions. ObdMonitorScheduler ($E9C5) walks the table, checks the enable conditions and calls each monitor whose status byte allows it. ObdMonitorInit ($E8EA) prepares the status bytes; it is called (from StoreMAPVoltsAndCalcMAPValue). [code]

Nothing calls ObdMonitorScheduler in B4CC. There is no JSR, JMP or pointer to $E9C5 anywhere in the ROM, so in 5269718 and 5007033 none of these monitors runs, although most of their fault descriptors are enabled. [code] The factory code bases B559, B4F3 and B4C2 call it from MainSubLoop on every pass, so in the factory 1995 calibrations the monitors do run; see code_bases.md. [code] The one exception is the O2 heater test, which runs from the key-off sequence; its result is stored but never processed into a code. This is the main piece of work for an OBD-II “Enhanced Edition”: the monitors exist, they only need to be scheduled, checked against the calibration and tested.

How the OBD-II executive works

Each monitor's status byte uses the same bits: 7 enabled this trip, 6 completed, 4 failed once (pending), 5 confirmed, 3 failed this trip, 2 test running, 0 fault to report. [code]

  • Scheduling. ObdMonitorScheduler runs a monitor when its status bit 7 is set and its mask at

$E931 allows this main-loop pass. Before each monitor it evaluates three condition lists from the calibration (EvalConditionList): the first suspends the monitor while the MIL is on, the other two set ObdStatusFlags bits 0 and 1 for the monitor to use.

  • Two-trip confirmation (ObdProcessMonitorResult). A first failure sets the pending bit and

stores a freeze frame with priority 1 (2 for misfire and fuel system). A second failure on a later trip turns the MIL on (ObdStatusFlags bit 7), stores the code through ThrowNonCriticalError and a freeze frame with priority 3 (4).

  • Similar conditions. Misfire and fuel system faults keep the RPM, MAP and closed-loop state of

the failure (records at $0129 and $012D). They heal only when the engine runs under similar conditions again (ObdSimilarConditions: MAP within $18, RPM within $0C).

  • Warm-up cycles. A trip counts as a warm-up cycle when coolant has risen by $16 from the start

value and reached $C7 (ObdWarmupCycleCheck). After 40 warm-up cycles without the MIL the codes are erased (ObdAutoClearCodes).

  • MIL off. After 3 good trips without a pending misfire or fuel system fault, the MIL goes off

(ObdMisfireMilLogic). A catalyst-damaging misfire sets ObdStatusFlags bit 3 (blink).

  • Readiness. ObdUpdateReadiness keeps ObdMonitorsComplete in J1979 PID $01 order and clears

a bit when its monitor completes.

The variables of each monitor are named in the RAM map (Cat…, Evap…, Egr…, O2Resp…, FuelSys…, Misfire…). Thresholds are calibration bytes in the $CB44-$CD41 range; most have no MP Tune name yet.

ISO 9141 / SAE J1979 (generic OBD-II)

HanldeISODiagnosticComs ($1ABA) is a state machine of 20 steps (DiagnosticRoutineTable). At the start of a session it sets the SCI to 10.4 kbaud, forces OC4 (PA4) high and sends $55, the ISO 9141-2 sync byte. Requests are collected in a buffer at $048E. [code]

IsoValidateRequest ($1E18) accepts a request only with the J1979 header $68 $6A $Fx, a correct sum checksum and the right length for the service. IsoBuildResponse ($1EEB) answers with the header $48 $6B $40. [code]

Service $02 (freeze frame) supports PIDs $00, $02 (code that stored the frame), $03-$07, $0B and $0C, read from the frame that CaptureFreezeFrame keeps at $011E. [code]

The calibration declares which monitors PID $01 reports as supported: $B81F = $07 (misfire, fuel system, components) and $B820 = $61 (catalyst, O2 sensor, O2 heater) in 5269718; $00 and $E1 (adds EGR) in 5007033. In B4CC the monitors themselves are dormant (see above), so a scan tool would never see them complete. [code]

Lamps

The check-engine lamp (pin 36) and the charge indicator lamp (pin 37) are controlled through bits 6 and 4 of $00EE (OutputBits2, called StartupSwitchMirror2 in the original disassembly). Flash codes are blinked by toggling bit 6, so bit 6 is the check-engine lamp. [inferred] Bit 4 is set from $0070 bit 7, which only charging-system faults set (flag bit 5), so bit 4 is most likely the charge lamp. [inferred] $00EE is sent to the I/O companion chip in the register frame with header $50; see ccd_and_link.md.

Companion chip link and CCD bus

Besides the SPI output driver, the HC11 talks over SPI to an I/O companion chip. That chip handles the CCD bus to the instrument cluster and body modules, drives the idle air stepper, the lamps and the TCC solenoid, and returns the switch inputs. The chip itself is not identified; all of this is reconstructed from the HC11 side. Confidence: [code] = follows directly from the code, [inferred] = likely.

Frame types

Frame Sent when Bytes out Bytes back
Command (1 byte) Default, every tick LinkCommandByte: stepper phase $B1, $AA, $A3, $9C (field 6, 5, 4, 3), hold $B8 (field 7), $95 once after start Status in bits 2-0: 6 sets BitFlags69 bit 1 (battery volts OK), 5 or 7 set BitFlags69 bit 4
CCD (5 bytes) LinkRequestFlags bit 7 (PrepareCCDDataForXmit_MM_1) $D0 (send) or $D8 (nothing), message ID, 2 data bytes, check The last received CCD message: ID, 2 data bytes, check
Register (4 bytes) LinkRequestFlags bit 6 (LinkRegisterUpdate) $48, $50 or $58, 16-bit value, check 16-bit value of the register
Frame C (4 bytes) LinkRequestFlags bit 5 (CODE1265) LinkFrameCHeader, 2 data bytes, check 2 bytes; purpose not decoded

The check byte is the complement of the sum of the bytes before it; the reply is checked the same way. After ten failed exchanges in a row LinkError pulses $0409 bit 3, which most likely resets the chip. [code]

Register frames

LinkRegisterUpdate cycles the header through $50, $58 and $48. The data sent with each header and the use of each reply:

Header Data sent Reply used as
$50 OutputBits2 and $00EF: lamps, TCC solenoid, O2 heater test switches (io_map.md) LinkInputWordHi/Lo ($00F0/$00F1)
$58 $0176/$0177 not used
$48 $00EC, $00 SwitchInputs ($00ED)

A reply is decoded against LinkRegLastAddress, the header of the frame before, so the chip answers one frame late (a pipelined SPI read). Which header means “write” and which register is read is therefore not certain; the table shows how the code pairs them. [code]

CCD messages received

PrepareCCDDataForXmit_MM_2 calls a handler by the low nibble of the received ID (CCDDataStream_2[CcdRxId & $0F]). [code]

ID low nibble Handler Action
1 CcdRx_1 Theft alarm input (sets CCDFlags5 bit 6, CCDFlags4 bit 4)
4 CcdRx_4 Stores data byte 1 in CcdRxValueA, restarts the CCD time-out
8 CcdRx_8 Stores data byte 1 in CcdRxValueB
other — Ignored

If no message with low nibble 4 arrives, CcdRxTimeout counts up and at $75 fault code 66 (“no CCD messages”) is reported. CCD_HandleAlarm keeps the theft alarm state in EEPROM4 bits 0-1 and is skipped when CONFIG bit 2 (alarm disable) is set. Which module sends IDs ending in 4 and 8, and what CcdRxValueA/B mean, is not decoded yet. [code] / [inferred]
