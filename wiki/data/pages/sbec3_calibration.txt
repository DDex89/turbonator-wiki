====== SBEC3: calibration ======
----

See also [[sbec3_overview|SBEC3 overview]] and [[sbec3_tuning|tuning notes (TunerPro, porting, open questions)]]. The full per-image table catalogue is generated into [[https://github.com/DDex89/neon-sbec3-firmware/tree/main/docs/catalogue|docs/catalogue/]] in the repository.

===== Where the calibration lies =====

The calibration is in bank 0, between the header at $00202 and the start of the code at $08000. The
reset code sets EK = 0, so the code reads it with plain extended addresses (''CMPA $19DC''). Nothing
in the code writes there: the area is read-only.

The code refers to it in two ways:

  * **Tables**, passed in X to one of four lookup routines (''LDX #table'', ''JSR Lookup2D''). The lookup
routines force XK = 0, so every table is in bank 0. 410 tables are found this way, between $0398
and $ABD7 (two small ones lie among the bank 0 code).
  * **Constants**, read directly: 1,449 different addresses, mostly with ''CMPA''/''CMPB'' (thresholds),
''LDAA''/''LDAB'' and ''LDD''/''CPD'' (16-bit values). Configuration bits at $0328-$0340 are tested
with ''BRSET''/''BRCLR''. See constants and option bits.

===== Table formats =====

All values are bytes. The formats follow from the lookup routines:

^ Format ^ Routine ^ Layout ^ 2GNT type ^
| 2D | ''Lookup2D'' ($0C08E) | n, flags, then n pairs (x, y), x ascending | C |
| 2D (y, x) | ''Lookup2DRev'' ($0C36A) | n, unused, then n pairs (y, x) |  |
| 3D | ''Lookup3D'' ($0C214) | rows, columns, signed flag, column axis (one byte per column), values row by row | A |
| 3D, no axis | ''Lookup3DNorm'' ($0C28C) | rows, columns, signed flag, values row by row | B |

Fault table: see below (2GNT type D).

**2D.** The input is compared with the x values; between two points the result is interpolated
linearly, outside the range it is the first or last y. The flags byte selects the arithmetic: $80
unsigned (320 of the 353 tables), $20 signed y, $10 steps without interpolation, $40 a zero y counts
as 256. Many 2D tables are followed by unused bytes up to a 12-byte slot (five points); whether a
table may be lengthened into that space has to be checked per table.

**3D.** The row input is a //position// 0-255 spread evenly over the rows (row = position x (rows-1)
/ 256). It usually comes from a 2D scale table that converts MAP into that position: the part-throttle
tables use ''PartThrottleMapScale'', the WOT tables ''WotMapScale''. The column input is searched on the
stored column axis (''Lookup3D'') or is also a position 0-255 (''Lookup3DNorm''). The result is
interpolated in both directions. Sizes in this image: 17 x 17, 9 x 17, 9 x 9, 5 x 9 and 5 x 5.

The signed flag ($FF) makes the values two's complement; the source shows them as negative decimals.

pulse width computed from MAP (next section).

''tools/autoname.py'' merges the hand names (''python3 tools/autoname.py hand.json'') and still gives a

===== Constants and option bits =====

''tools/constants.py'' finds every byte or word the code reads directly with extended addressing and
that is not part of a table: 1,449 of them in 05293190AC (1,264 bytes, 181 words, 4 longs; two more,
the row counts after ''FaultStatusMap'', are named by hand because the code reaches them through X), among
them 21 option bytes tested with ''BRSET''/''BRCLR'' (120 bits used). They are kept with the tables in
the ''scalars'' of ''annotations/tables.json'', so the sources show ''CMPA >IdleCoolantMin'' instead of
''CMPA $2853'', the catalogue lists them with value and physical value, the XDF has them as constants
(and every option bit as a flag), and the port carries them to the other images (from 239 in family
A to 1,404 in family E).

All 120 used option bits are described in ''annotations/bits.json''. The polarity was read from the
code: most bits switch a function on (''BRCLR'' skips it when the bit is clear), a few switch it off
(for example $033A.7 skips the idle flare check, $0328.0 the SKIM handling). Bits that only pick one
of two code paths without a clear purpose are described as "selects a branch in ...". Settled ones
include $032C.7 closed loop off, $032C.6 flex fuel, $032E.6 manual transmission, $032E.2 PCI bus
instead of CCD, $032F.7-4 the O2 sensors fitted (upstream 1 and 2, downstream 1 and 2) and
$033F.7-4 the matching heater monitors. The XDF puts the text in the description of each flag.

For each constant the script looks at how it is used: what the register held before the compare,
add or subtract (''LDAA >CoolantTemp,Z'' then ''CMPA $2853''), or what a loaded value is compared with
or stored into. That gives the unit (temperature, rpm, kPa, volts) and a structural name: the
prefix of the tables of the same routine or the subsystem, the variable, and the role (''Thresh'' for
a compare, ''Adder'', ''Offset'', ''Factor'', ''Init'' for a value stored into RAM, ''Value'' otherwise),
numbered when repeated. All 1,451 constants now have hand names from the code that reads them;
where the purpose is not certain the description says "probably". The structural name and the *
in the catalogue remain only for constants found in a new image and not yet named. Word rpm values use the unit ''rpmw'' (rpm = x / 8).

state in 05293190AC:

===== Fuel pulse width =====

''CalcFuelPulse'' ($11F40) runs from the input-capture 1 interrupt, that is on every reference
event:

  - Part throttle or WOT is chosen by ''FuelModeFlags'' ($0771,Z) bit 5; this selects the constants, the scale table
and the fuel table.
  - Base pulse width = (Map - MapOffset) x (256 + K) / 16, or zero if MAP is below the offset. With
calibration bit $0337.2 set, MAP is first raised to the lowest point of the part-throttle scale.
  - The fuel table gives a signed value v (rows by MAP through the scale table, columns by
''EngineRpm'', whose high byte is rpm / 32); the base is multiplied by 1 + v / 256.
  - ''BaroFuelAdder'' ($080E,Z) is added and the result is stored in ''FuelPulse'' ($07E2,Z) and ''Temp4F6'' ($04F6,Z).

So the fuel tables work like a volumetric-efficiency correction on a linear MAP model, with the
two constants setting the slope and the zero point. Dead time, temperature and other corrections
are applied elsewhere (stage 5).

''InjectorDeadTime'' is looked up with ''BatteryVolts2'' ($0A51,Z) as input. 2GNT lists a fix that changes this to
''BatteryVolts'' ($0A50,Z) (''BatteryVolts''); who writes $0A51 has not been checked yet.

sensor (''FlexSensorRaw'', $0A8E,Z) and the flex-fuel learning code (''FlexLearn...'', around

spark tables and in the cranking table. Calibration bit $032C.6 enables it; in 05293190AC (a
gasoline car) the flex tables are neutral.

===== Fault table =====

''FaultTable'' ($4052) has 256 rows of 10 bytes:

^ Byte ^ Content ^
| 0 | row number |
| 1 | trigger count |
| 2 | blink code (BCD, as flashed by the check-engine lamp) |
| 3 | attribute bits |
| 4, 5 | mask and byte offset of the fault bit in the fault bit array |
| 6, 7 | P-code (BCD): $03 $40 = P0340 |
| 8, 9 | unused (zero) |

83 rows carry a P-code; the list is in the catalogue. Codes for cylinders 5 and 6 (P0205, P0206,
P0355) are present, so the program also covers six-cylinder engines.

===== OBD monitor table and condition lists =====

''ObdMonitorTable'' ($20000, in the code area) has 16 rows of 20 bytes, one per OBD monitor, read by
''ObdMonitorMain'': the record offset, the monitor status byte (''MonStatus*''), the run period (low
six bits of byte 5, tested against ''MainLoopCounter''), the fault table row of the monitor's P-code,
the addresses of three condition lists, and the result byte and bit. The rows show which status
byte belongs to which code: ''MonStatusCatBank1/2'' are the catalyst monitors (P0420, P0432),
''MonStatusO2Resp1/2'' the O2 response monitors (P0133, P0153), ''MonStatusO2Sensor1-4'' the heater
monitors (P0135, P0155, P0141, P0161), and the fuel system monitors give P0171/P0174 for "too lean"
(adaptive at its upper limit) and P0172/P0175 for "too rich". The fuel system routines and
constants were renamed after this (''FuelSysTooLean//'', ''FuelSysTooRich//'').

''ConditionTable'' ($20B1C) checks such a list: a count, then 4-byte entries of RAM offset, test and
mask. Test 0 needs the masked bits clear, test 2 needs them all set, test 4 needs the value above
the mask byte; the check fails at the first entry that does not hold. The 48 lists lie in bank 0
between $33CA and $4015 and are laid out in the source with each entry decoded, for example
''CatBank1Conds1'': the catalyst monitor runs only while none of 19 bytes of stored faults (''FaultMem*'',
about 70 P-codes) are set. These lists are calibration: changing them changes which faults suspend
which monitor.

Two more data blocks of bank 0 are laid out with their entries decoded. ''FaultStatusMap'' ($758C,
44 rows of 10 bytes) ties a fault table row to a monitor status byte and bit, and for the 22
two-trip tests (rows 11-32, searched by ''ObdFaultReport'') to a second pair: ''MonFlags09D-09F'' hold
the pending bits (failed once, fault not reported yet) and ''SwitchMonFlags'', ''O2MonFlags'',
''MonFlags65A'' the result each monitor hands over (set = failed), so their bits now have P-codes (P0740,
P1899, P0703, P0500, P1294, P0125, P1281, P0551, the O2 and fuel level codes). ''BitCollectMaps''
($713B, 29 maps of 32 bytes) are the input of ''CollectBits'': eight entries of RAM offset, mask and
output bit build one byte, for the switch inputs and for the status bytes the SCI and bus messages
send.

Lists of RAM addresses in the code banks are laid out with each word named: the EEPROM map
(''EepromShadowMap'', $38448: EEPROM word and the RAM copy), the descriptors of the O2, O2 heater,
downstream O2 and catalyst monitors, the OBD record pointers, the CCD transmit rotation and eight
lists the SCI diagnostic service probably sends from (''DiagDataList1-8'').
